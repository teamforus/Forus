# Webshop translations

How text is translated on the websites, and how to change it safely. Please be aware that the Dutch language is leading, the other languages are machine translated and are not requiered for a PR. In most cases, we actually prefer you to just add the Dutch texts and we will conduct the translations during the PR review. So, only use this for testing or development learning purposes.

## TL;DR

- Dutch (`nl`) is the source of truth.
- All other languages are generated by DeepL via scripts in `forus-frontend/translations/`.
- Generation of the other languages is optional.
- Edit **only** the Dutch `.mjs` source files. Regenerate everything else with one command.
- Never hand-edit `translations/cache/cache.json` or `react/src/webshop/i18n/translated/*.json`.

## Scope

These scripts translate the **webshop** only (`react/src/webshop/i18n/...`). The dashboard has its Dutch strings hardcoded in components and services; changing those today is manual per file.

## Static Texts Documentation

Static texts are the fixed words and messages in the app. This includes the interface labels, validation messages, and error texts used by both the frontend and the backend. The translation process uses a series of automated steps to update and add new translations using DeepL API. The process is split into several commands that work in sequence.

---

### Frontend Static Texts

The frontend uses i18next and react-i18next npm libs. All the original texts are stored in JavaScript modules (files ending in `.mjs`) under `react/src/webshop/i18n/`.

#### Step 1: Translations Prepare

- **What it does:**
  - Combines the source texts (from files like `i18n-nl.mjs` and other `nl*` files).
  - Compares these texts to the previous run using `translations/cache/cache.json`.
  - Creates two files in the cache folder:
    - **cache_added.json:** Contains new texts or texts that have changed.
    - **cache_removed.json:** Contains texts that were removed.
- **How to run:**
  - Run the command:  
    ```bash
    npm run translations-prepare
    ```
- **Why:**  
  Prepares a “diff” so that only new or updated texts are sent for translation.

#### Step 2: Translations Translate

- **What it does:**
  - Reads the new or changed texts from `cache_added.json`.
  - Uses DeepL to translate these texts to all the target languages.
  - Saves the translations as files (e.g., `cache_translated_en-US.json`, `cache_translated_uk.json`) in the same cache folder.
- **How to run:**
  - Run the command:  
    ```bash
    npm run translations-translate
    ```
- **Why:**  
  This step automatically translates your texts using the DeepL API.

#### Step 3: Translations Apply

- **What it does:**
  - Takes the translated texts from the cache.
  - Creates or updates the final translation files in `react/src/webshop/i18n/translated/` (for example, `en-US.json`, `uk.json`).
  - These files are used by the React app when it displays the interface.
- **How to run:**
  - Run the command:  
    ```bash
    npm run translations-apply
    ```
- **Why:**  
  This makes the new translations available in the app immediately.

#### Step 4: Translations Update Cache

- **What it does:**
  - Updates the main cache file (`cache.json`) with the newly translated keys.
  - Removes keys that no longer exist, based on `cache_removed.json`.
- **How to run:**
  - Run the command:  
    ```bash
    npm run translations-update-cache
    ```
- **Why:**  
  This ensures that the next time you run the process, the script only translates texts that have changed.

#### Combined Command

- **Quick Start:**  
  You can run all the above steps in one go with:
  ```bash
  npm run translations-run-all
  ```
- **Why:**  
  This is the easiest way to update all translations without running each command manually.

#### Frontend Configuration

- **Setup File:**  
  Create a file named `deepl.env.mjs` in the root of the frontend.
- **Using the Example File:**  
  You can start by copying the example:
  ```bash
  cp deepl.env.example.mjs deepl.env.mjs
  ```
- **Edit the File:**  
  Make sure the file includes:
  ```js
  export default {
      testMode: false,
      accessKey: 'YOUR-DEEPL-API-KEY',
      sourceLanguage: 'nl',
      targetLanguages: ['en-US', 'pl', 'ar', 'tr', 'de', 'uk', 'ru', 'fr'],
  };
  ```
  - **testMode:** Set to `false` in production.
  - **accessKey:** Your DeepL API key.
  - **sourceLanguage:** Always set to `'nl'` (Dutch).
  - **targetLanguages:** A list of languages you want to translate to.

#### Test Mode
If testMode is set to true, the original text will be returned with the target locale as a prefix instead of calling the DeepL API.

### Backend Static Texts

The backend static texts (like validation errors and interface texts) follow a similar process using Laravel artisan commands. The source files are located in `resources/lang/nl/`.

#### Step 1: Prepare

- **What it does:**
  - Reads all original language files from `resources/lang/nl/`.
  - Compares them with a cache file at `storage/translations-caches/cache.json`.
  - Creates two new files in `storage/translations-caches/`:
    - **cache_added.json:** Contains new or updated texts.
    - **cache_removed.json:** Contains texts that have been removed.
- **How to run:**
  ```bash
  php artisan translate:static prepare
  ```
- **Why:**  
  Prepares the list of texts that need translation by finding differences.

#### Step 2: Translate

- **What it does:**
  - Translates all texts in `cache_added.json` for each target language.
  - Stores the results in files like `cache_translated_en.json` inside the cache folder.
- **How to run:**
  ```bash
  php artisan translate:static translate
  ```
- **Why:**  
  Uses DeepL (or the configured provider) to automatically translate the new or changed texts.

#### Step 3: Apply

- **What it does:**
  - Creates or updates the final translation files in the `resources/lang/` folder (for example, `en.json`, `uk.json`).
  - These files are used by Laravel when showing texts in the application.
- **How to run:**
  ```bash
  php artisan translate:static apply
  ```
- **Why:**  
  Makes the updated translations available to the backend.

#### Step 4: Update Cache

- **What it does:**
  - Updates `storage/translations-caches/cache.json` with new translations.
  - Removes keys that are no longer present.
- **How to run:**
  ```bash
  php artisan translate:static update-cache
  ```
- **Why:**  
  Keeps the cache current so that future runs only process changes.

#### Combined Command

- **Quick Start:**  
  To run all steps at once, use:
  ```bash
  php artisan translate:static run-all
  ```
- **Why:**  
  This runs all four steps in order, making it easier to update everything in one command.

#### Backend Configuration

- **Main Config File:**  
  Check the file `config/translation-service.php` for all backend settings.
- **Important Settings:**
  - **source_language:** Always set to `'nl'`.
  - **target_languages:** A comma-separated list in the env variable `TRANSLATION_SERVICE_TARGETS`.
  - **provider:** Usually set to `'deepl'` (or `'debug'` for testing).
  - **DeepL Settings:** Include your DeepL API key and whether you are using a free or paid account.
- **How to Adjust:**
  - Update these values in your `.env` file as needed.


#### Provider debug  
When provider is set to 'debug', the original text will be returned with the target locale as a prefix instead of calling the DeepL API.

## How to Use the Static Texts Translation Process

1. **For Updating Existing Translations:**
   - Ensure your configuration files (like `deepl.env.mjs` and `.env`) are set correctly.
   - Run the combined command:
     - Frontend:  
       ```bash
       npm run translations-run-all
       ```
     - Backend:  
       ```bash
       php artisan translate:static run-all
       ```
   - Check your git diff (if applicable) to see the changes.

2. **For Adding a New Language:**
   - **Step 1:** Update all existing translations using the run-all commands.
   - **Step 2:** Commit any changes (optional, but recommended).
   - **Step 3:** Update your configuration to include only the new language in the target languages list.
     - For example, update `deepl.env.mjs` or `TRANSLATION_SERVICE_TARGETS` to include just the new language like `'ro'`.
   - **Step 4:** Remove the cache file (`translations/cache/cache.json` for frontend or clear the backend cache file) so that the system knows to translate everything new.
   - **Step 5:** Run the run-all commands.
   - **Step 6:** After confirming the new translation file (e.g., `react/src/webshop/i18n/translated/ro.json` or `resources/lang/ro.json`) is correct, update your configuration to add back all previous languages along with the new one.


## Database Static Texts

### What Are Database Static Texts?

- **Database Static Texts** are fixed texts stored in the database.
- They are found in tables like:
  - **tags** (column: name)
  - **record_types** (column: name)
  - **business_types** (column: name)
  - **product_categories** (column: name)
  - **record_type_options** (column: name)
- Each table has a companion translation table that holds the translated values.  
  *Example:*  
  The table `record_types` has a companion table `record_type_translations` with columns like:
  - `id`
  - `locale`
  - `record_type_id`
  - `name` (translated value)

### How It Works

1. **Storing Translations:**
   - When a text needs to be translated (for example, a record type name), a new row is created in the companion translation table for each target language.
   - **Example:**  
     For a record type with key `first_name`:
     - In Dutch (`nl`):  
       `[record_type_translations] → locale: nl, name: Voornaam`
     - In English (`en`):  
       `[record_type_translations] → locale: en, name: First name`

2. **Translation Cache:**
   - A cache is maintained in the `translation_caches` table.
   - This table stores:
     - `translatable_type`: the name of the table/model.
     - `translatable_id`: the ID of the row.
     - `key`: which column is translated.
     - `value`: the translated text.
     - `locale`: the source language (always `nl` in our case).
   - The cache helps the translation command know which texts have already been translated so that it does not translate them again.

### Running the Translation Command

Translations for database texts are generated by a single command. You can translate all tables at once or choose a specific table/model.

#### To Translate All Tables

Run the following command:
```bash
php artisan translate
```

#### To Translate a Single Model/Table

For example, to translate only the record types, run:
```bash
php artisan translate --model App\\Models\\RecordType
```
> **Note:** Use two backslashes (`\\`) in the model namespace.

The list of models (or tables) that use translations is available in the configuration file `config/translation-service.php`.

### How to Use: Step-by-Step

1. **When Texts Are Added or Updated:**
   - If new rows are inserted or existing rows are updated in any of the listed tables, simply run:
     ```bash
     php artisan translate
     ```
   - Or, if you want to update just one table, use the `--model` option as shown above.
   - **Remember:** Since the translations are stored in the database, these changes need to be applied on every environment (e.g., development, staging, production). They will not appear as file changes in git.

2. **When Adding New Languages:**
   - **Step 1:** Make sure that all texts for the existing languages are up to date. Run:
     ```bash
     php artisan translate
     ```
   - **Step 2:** Clear the translation cache by removing all rows from the `translation_caches` table. This is necessary because the command will skip texts that are already in the cache.
   - **Step 3:** Update your environment variable `TRANSLATION_SERVICE_TARGETS` to include **only the new language**.
   - **Step 4:** Run the translation command again:
     ```bash
     php artisan translate
     ```
   - **Step 5:** Verify that the `translation_caches` table has been repopulated and that translations for the new language are present.
   - **Step 6:** Finally, update `TRANSLATION_SERVICE_TARGETS` to include all previous languages plus the new one.

### Configuration

- **Same Config Files:**  
  Database static texts use the same configuration files as the other static texts (check `config/translation-service.php`).
- **Important Variables:**
  - `TRANSLATION_SERVICE_TARGETS`: A comma-separated list of locales for the translations.
  - Other settings (like the provider and API keys) work the same way as described in the Static Texts documentation.


## On Demand Translations

### What Are On Demand Translations?

- **On Demand Translations** are used for texts that users can change.  
- Instead of translating all texts ahead of time, translations are only generated when a user requests them.  
- The first user who needs a translation triggers a call to the translation API (DeepL) to translate that text.  
- Once a text is translated, the result is saved in the database so that other users can use it without another API call.

---

### How the Process Works (Workflow)

1. **User Request:**
   - A user (UserA) opens the webshop and switches the language from Dutch (`nl`) to English (`en`).

2. **Checking for Existing Translations:**
   - The backend checks if the page's texts already have an English translation.

3. **Generating Translation:**
   - If the translation is not available, the backend calls the DeepL API.
   - The API translates the text, and the translation is saved in the database.

4. **Using the Translation:**
   - The translated text is returned to UserA.
   - If UserA or another user (UserB) requests the same text later, the backend finds the saved translation and sends it immediately without making another API call.

5. **Handling Changes:**
   - If the original text changes (for example, a product name is updated), then only the changed text is retranslated when requested.  
   - All other texts use the already stored translations.

---

### How Translations Are Stored

Translations for on demand texts are saved in the `translation_values` table with the following fields:

- **id:** A unique identifier.
- **translatable_type:** The name of the table (or type) where the original text is stored.
- **translatable_id:** The ID of the record in that table.
- **key:** The name of the column that was translated.
- **locale:** The target language (for example, `en` for English).
- **organization_id:** The ID of the sponsor organization (used for statistics and cost estimates).
- **implementation_id:** The ID of the specific implementation (also for statistics and cost estimates).
- **from:** The original text that was translated.
- **from_length:** The length of the original text (useful for cost estimation).
- **to:** The translated text.
- **to_length:** The length of the translated text (not used much right now).


---

### Configuration Details

On demand translations use the same configuration files as static and database translations. In addition, there are a few extra settings:

#### Price and Limit Settings

- **price_per_mil:**  
  This setting (e.g., `TRANSLATION_SERVICE_PRICE_PER_MIL`) is used to estimate the cost for translations in the sponsor dashboard.
  
- **max_monthly_limit:**  
  This defines the maximum number of characters allowed per month (e.g., `TRANSLATION_SERVICE_MAX_MONTHLY_LIMIT`).

#### Caching Settings

Since checking if a translation is up to date can create many database requests, caching can help:

- **cache_enabled:**  
  Turn caching on or off (e.g., `TRANSLATION_SERVICE_CACHE_ENABLED`).

- **cache_driver:**  
  Choose the cache driver. By default, it might be set to `file`, but if you have a faster option like Redis or Memcache, you can change it (e.g., `TRANSLATION_SERVICE_CACHE_DRIVER`).

- **cache_time:**  
  This sets how long the translation results should be cached (in seconds, e.g., `TRANSLATION_SERVICE_CACHE_TIME`).

Using a faster cache driver (like Redis) is recommended if available. 

## Enabling Translations for an Organization

### 1. Activate Translations for the Organization

- **Database Flag:**  
  - Set the `allow_translations` field to `1` in the **organizations** table for the organization you want to enable translations for.
  - This action will enable the translation user interface (UI) for the sponsor of that organization.

### 2. Enable Translations in the Sponsor Dashboard

- **Access the Dashboard:**  
  - Log in to the sponsor dashboard.
- **Find Translation Settings:**  
  - Look for the **Translations Settings** section.
  - Here you can turn on translations for the organization.  
    - *(Alternatively, you can also set `translations_enable` to `1` directly in the organizations table if needed.)*

### 3. Set Translation Limits

- **Daily, Weekly, and Monthly Limits:**  
  - In the organizations table or via the dashboard’s Translations Settings page, set:
    - **translations_daily_limit**
    - **translations_weekly_limit**
    - **translations_monthly_limit**
  - These limits control how many characters can be translated within a day, week, or month.
  - **Note:** These limits are shared across all implementations of the organization.

### 4. Enable Languages for Each Implementation

- **Multiple Implementations:**  
  - An organization can have multiple implementations. Each implementation can have its own list of enabled languages.
- **How to Enable:**
  - Go to the **Implementations List** on the dashboard.
  - Click on the **Translations** button for the desired implementation.
  - In the implementation languages page, select the languages that should be available on the webshop.

---

### Summary

- **Step 1:** Enable translations by setting `allow_translations=1` (or `translations_enable=1`) for the organization.
- **Step 2:** Access the sponsor dashboard and enable translations in the Translations Settings.
- **Step 3:** Configure the daily, weekly, and monthly translation limits.
- **Step 4:** For each implementation, choose which languages should be available on the webshop.
